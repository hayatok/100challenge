# Frontend Guidelines

このファイルは、フロントエンド実装における共通ルールを定義する。
プロジェクト固有の見た目やブランド方針は `docs/DESIGN.md` を優先する。

## Core principle

UIは、装飾のためではなく、ユーザーが目的を達成するために存在する。

優先順位は以下とする。

1. 内容と目的の分かりやすさ
2. 操作のしやすさ
3. 情報の見つけやすさ
4. 状態の分かりやすさ
5. 視覚的な一貫性
6. 装飾や演出

## Reuse existing patterns

- 既存のデザインシステム、コンポーネント、トークンを最優先する
- 同じ意味のUIに複数の見た目を作らない
- 既存のボタン、入力欄、モーダル、テーブル、タブ、通知を再利用する
- 新しいコンポーネントを作る前に、既存部品で表現できない理由を確認する
- 画面ごとに独自の余白や角丸を追加しない
- 既存のアイコンライブラリがある場合は、それを使う
- 手描きSVGや絵文字をUIアイコンとして追加しない

## Layout and hierarchy

- 画面の主目的が最初に分かる構造にする
- 主要操作を目立たせ、補助操作と明確に区別する
- 情報の重要度に応じて、文字サイズ、太さ、余白を使い分ける
- ページ全体を理由なくカード化しない
- カードを入れ子にしない
- ページセクションは、原則として余白、罫線、背景帯、見出しで構成する
- 繰り返し表示される項目や、明確にまとまったツールにのみカードを使う
- 装飾的なグラデーション、光球、ぼかし、過剰な影を追加しない
- 画面上の要素を増やす前に、本当にユーザーの判断や操作に必要か確認する

## Controls

コントロールの種類は、その操作の意味に合わせる。

- 2値の設定にはトグルまたはチェックボックスを使う
- 複数の表示モードにはタブまたはセグメントコントロールを使う
- 選択肢が多い場合はメニューやセレクトを使う
- 数値には入力欄、ステッパー、スライダーを使う
- undo、redo、save、download、zoomなど既知の操作にはアイコンを使う
- 意味が分かりにくいアイコンにはツールチップを付ける
- アイコンだけのボタンには、キーボード操作とアクセシブルな名前を用意する
- ボタンのラベルは、実行される動作を具体的に表す

## States

インタラクティブな画面では、必要に応じて以下の状態を用意する。

- 初期状態
- loading
- empty
- success
- error
- disabled
- hover
- focus
- pressed
- validation error
- permission denied
- offlineまたは通信失敗

状態ごとに、ユーザーが次に何をすべきか分かるようにする。
エラーを色だけで伝えない。必要に応じて説明文や再試行操作を用意する。

## Responsive behavior

最低限、以下の幅で確認する。

- 375px
- 768px
- 1024px
- 1440px

確認項目:

- 文字が親要素からはみ出さない
- ボタンや入力欄が押しつぶされない
- ナビゲーションが意図せず折り返されない
- 表や長い文章が画面を壊さない
- hoverに依存した操作がモバイルで使えなくならない
- 画面幅によって主要操作の優先順位が変わらない
- 固定サイズの要素が内容によって移動・拡大しない
- 横スクロールが発生する場合は意図したものか確認する

## Typography

- 表示場所に合った文字サイズを使う
- ヒーロー用の大きな文字を、サイドバー、カード、フォーム、ダッシュボードで使わない
- 文字サイズを画面幅に応じて無制限に拡大しない
- 長いラベルがボタンやカード内で欠けないようにする
- 見出し、本文、補助文、数値、ラベルの階層を明確にする
- 文字間隔を不自然に詰めない
- 日本語では、行長、禁則処理、改行位置を確認する

## Color and surfaces

- `docs/DESIGN.md` のカラートークンを使う
- 新しい色を追加する前に、既存色で表現できないか確認する
- 画面全体を単一の色相で埋め尽くさない
- 背景、境界線、本文、補助文、状態色のコントラストを確認する
- 状態を色だけで伝えない
- 重要な要素だけにアクセントカラーを使う
- 表面、罫線、影の役割を混同しない

## Assets and icons

- プロダクト、人物、場所、データ、状態を表す画像は、可能な限り具体的な素材を使う
- ただの装飾画像を主要コンテンツの代わりにしない
- 既存のブランド素材や画像がある場合は、それを優先する
- プレースホルダー画像を最終UIに残さない
- アイコンのサイズ、線幅、配置を統一する
- アイコンを追加するだけで操作を説明したつもりにしない

## Accessibility

- キーボードだけで主要操作を完了できるようにする
- focus状態を見えるようにする
- 色のコントラストを確認する
- フォームにはラベルとエラーメッセージを付ける
- ボタンとリンクを意味に応じて使い分ける
- 画像には適切な代替テキストを付ける
- モーダル、ドロップダウン、ポップオーバーのフォーカス移動を確認する
- 補助技術にとって意味のあるHTML構造を使う

## UI change workflow

UI変更では、以下の順番を守る。

1. 現在の画面をブラウザで確認する
2. 変更箇所を1つに絞る
3. 既存の部品とトークンを探す
4. 最小限の実装を行う
5. ブラウザで変更結果を確認する
6. デスクトップとモバイルを確認する
7. 各状態を確認する
8. スクリーンショットで重なりや欠落を確認する
9. 実装とデザインルールの不一致を確認する

## Completion checklist

- [ ] 目的が画面上ですぐ分かる
- [ ] 主操作が明確である
- [ ] 既存コンポーネントを再利用している
- [ ] 不要なカード、グラデーション、装飾を追加していない
- [ ] loading、empty、error、successを確認した
- [ ] キーボード操作を確認した
- [ ] 375px幅で確認した
- [ ] 1440px幅で確認した
- [ ] 文字の欠落・重なり・はみ出しがない
- [ ] 既存画面と視覚的に一貫している
- [ ] テストまたはbuildを実行した
