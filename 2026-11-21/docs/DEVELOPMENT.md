# Codex ゲームショーケースから取り入れる開発手順

[OpenAI のゲームショーケース](https://developers.openai.com/showcase/games) に掲載された29件を確認した。28件には制作ステップや反復の記録があり、[Turn-based RPG](https://developers.openai.com/showcase/turn-based-rpg) は完成結果のみを掲載していた。ステップの中には、元の依頼を再構成したプロンプトや制作概要だけのものもある。ここでは、それらから今日のアプリに取り入れられる手順をまとめる。

## 制作事例から取り入れること

| 事例 | 今日のアプリで使う方法 |
| --- | --- |
| Void Explorer は、プレイヤーができることと、移動中に守る条件を示してから技術構成を検討した。 | 最初の依頼では操作、移動先、画面の応答など、プレイ中に観察できる条件を伝える。条件を満たせる構成を Codex に提案させる。[制作記事](https://developers.openai.com/blog/how-to-build-games-with-astra) |
| Hollowflux は水が反応する短い戦闘から始め、操作を調整してから進行や装備を増やした。 | ゲーム固有の仕組みと主操作が一緒に動く場面を先に作る。その場面を繰り返し遊び、反応の分かりやすさを確認する。[制作手順](https://developers.openai.com/showcase/hollowflux) |
| Sunwake はコンセプトを選んで操船を試作し、船の動き、浮力、航跡、しぶきを結び付けた。 | 参考画像には実装で守りたい特徴を書き添える。動きに合わせて変わる演出は、対象の速度や状態との対応まで確認する。[制作手順](https://developers.openai.com/showcase/sunwake) |
| Velocity Loop はコース選択とレース中の画面を検討し、完成段階でスマートフォンの主操作を確認した。 | コンセプトに選択画面とプレイ中の HUD を含める。対応する入力方法ごとに、開始から結果、再試行まで操作する。[制作手順](https://developers.openai.com/showcase/velocity-loop) |
| Little Ritual は配達ループを先に作り、後から再生成できる Blender ソースと、可動部に名前を付けた GLB を用意した。 | 見た目の決定に先立って遊びを試作する方法もある。編集する素材は原本とゲーム用の出力を分け、書き出した素材をゲーム内で確認する。[制作手順](https://developers.openai.com/showcase/little-ritual) |
| Void Explorer は繰り返し呼び出せる場面とゲーム状態の参照手段を設け、通常操作で進むテストも用意した。 | 特定場面で状態と見た目をすぐ確認できるようにする。場面を呼び出す検証に加え、プレイヤーが実際にたどる経路を通す。[制作記事](https://developers.openai.com/blog/how-to-build-games-with-astra#give-astra-a-way-to-inspect-and-play) |
| Tidegarden は水面を診断しやすい表示を作り、描画負荷を調べてからコストを下げた。 | 描画が重いときは、対象端末と計測場面をそろえてフレーム時間などを測る。変更後は負荷と見た目の両方を同じ場面で確認する。[制作手順](https://developers.openai.com/showcase/tidegarden) |

## 開発フォルダの構成案

以下は `100challenge` の日付単位の構成に合わせた案。今ある `AGENTS.md` とこの開発ガイドから始め、ほかのファイルやディレクトリは用途が決まった時点で作る。

```text
2026-11-21/
├── AGENTS.md                 # 開発方針と採用した実行・検証コマンド
├── README.md                 # 遊び方、必要な環境、起動方法
├── docs/
│   ├── DEVELOPMENT.md        # この開発ガイド
│   ├── SPEC.md               # 主操作、試作範囲、完了条件
│   ├── ART_DIRECTION.md      # 画風や HUD の方針。資料が増えたら作る
│   └── verification/
│       ├── RESULTS.md        # 再現条件、実施結果、未確認事項
│       └── screenshots/      # 比較や報告に使う実画面
└── art/                      # 採用した参考画像、編集用の原本、素材の出典
```

| 構成を選んだら | 追加するもの |
| --- | --- |
| Vite などのビルド環境を使う Web ゲーム | 日付フォルダ直下に実際のビルド設定、`src/`、必要に応じて `tests/` を置く。ゲーム用素材はビルド環境の読み込み方法に合わせる。 |
| ビルドなしの小さな Web ゲーム | 日付フォルダ直下に `index.html` を置き、必要なスクリプトと素材を追加する。 |
| Godot | `game/` に `project.godot` とゲーム用素材を置き、シーンやスクリプトはエンジンから参照できる場所にそろえる。 |

採用した素材ごとに、出典や生成条件と、ゲームが読み込むファイル名を記録する。公開時は、日付付きの配信先でも画像や音声が読み込まれるかを確認する。[カタログ登録と Pages の手順](../../README.md)

## 試作から検証まで

1. **最初の依頼を具体化する。** 誰が何を操作し、どうなれば一区切りかを一文にする。最初に遊べる場面、そこで外せない挙動、対象端末と入力方法、見た目の目標を `docs/SPEC.md` に書く。画風が不明なら同じ場面の候補を比べ、操作感が最大の不確実性なら短い試作を先に作る。
2. **一回分を通して遊ぶ。** 開始から主操作、結果、再試行をつなぐ。遊んで見つけた問題は「どの場面で、どんな入力をすると、何が起きるか」で記録する。次の変更は、改善を確かめられる範囲に絞る。
3. **再現と通しプレイを両方行う。** 再現に時間がかかる場合は、固定シードや指定した初期状態から開始できる開発用の入口を用意する。対応する環境で画面と状態を確認し、通常の入力だけで対象場面まで進む手順も試す。再発の影響が大きいルールや操作には、採用環境に合った自動テストを検討する。
4. **結果を残す。** 画面の比較には同じ場面・視点・画面サイズを使う。検証記録には端末・入力、手順、観測した結果、未確認事項を記入し、必要なときだけ実画面を添える。コンセプト画像は `art/` に置く。操作の気持ちよさや楽しさは、人が遊んだときの所感として記録する。

Void Explorer では、同じシードから同じ地形を生成できるかを Vitest、着陸後に船を降りて歩けるかを Playwright で検証している。今日のアプリでも、入力と結果が明確なゲームルールと、実際の画面や操作を通す検証は、それぞれに合った方法を選ぶ。[制作記事](https://developers.openai.com/blog/how-to-build-games-with-astra)
