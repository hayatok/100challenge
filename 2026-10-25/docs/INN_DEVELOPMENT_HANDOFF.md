# 「六部屋の約束」開発引き継ぎ

作成日：2026-10-25（日本時間）。この資料は、企画と調査を別のセッションでの開発へ引き継ぐために作った。ゲーム本体はまだ実装していない。まず読む資料と、最初の開発で確かめることを以下にまとめる。

## 1. ユーザーの意図と現在地

ユーザーは、確立したジャンルを組み合わせた本編ゲームを作りたいと考えている。六案を比較した後、「六部屋の約束」が良さそうだと述べた。ギャルゲー要素と、令和の萌えキャラ・萌え要素も希望している。過去にこのリポジトリで作ったゲームを、新作のアイデア元にしてはいけない。

企画は「宿屋経営 × 宿泊条件の交渉」。六部屋の宿を二人のヒロインと営み、客と交わした約束を守りながら営業を続ける。契約によって、今夜の売上だけでなく、翌夜以降に貸せる部屋や提供できる食事が変わる。営業後には、その日の判断を二人と話し、仕事仲間としての信頼や恋愛関係を育てる。

完成版の企画上の目標は十八夜、全体3〜6時間、1回10〜20分。所要時間と4〜6か月という工数は仮見積もりで、実測値ではない。後述する三夜の試作は、本編を作る前の検証用である。完成版を三夜のミニゲームへ変更する提案ではない。

これまでに企画書、生成イメージ、画面モック、ゲーム設計の調査、設計スキルを作った。画面モックは説明を切り替える見本で、契約処理や保存を実装したゲームではない。技術スタックも未決定である。

ユーザーは、主語・目的語・文のつながりが曖昧な企画書を強く批判した。説明では、誰が何をし、その結果何が変わるのかを具体的に書く。未確定の仕様を、分かりにくい言い回しで決定済みに見せない。

## 4. 企画に記載した基本仕様

以下は実装済みの仕様ではなく、開発の出発点となる企画上の仕様である。変更した場合は、理由と影響を実装先の文書へ残す。

| 項目 | 企画上の内容 |
| --- | --- |
| 宿の規模 | 六部屋。清掃・修繕中は貸せない。二重予約は不可 |
| 厨房 | 一日に最大八食。食事を提供する能力と、使う食材の在庫を区別する |
| 交渉 | 一夜四枠。客一組に最大二案を提示でき、断られても使用した枠は戻らない |
| 予約の範囲 | 今夜を含む三夜。確定前に、案を採用した後の空室・食事の余力・入出金を確認できる |
| 客の条件 | 必須条件、予算上限、承諾する範囲を表示。条件を満たす案は確実に承諾される |
| 事情を聞く | 一枠で不明な希望を知る。ただし、その情報が何を変えるかは未解決 |
| 契約と営業 | 契約時に料金を受け取り、部屋と食事を確保する。食材は購入時に支払う。営業終了時に宿泊、食事、清掃、維持費を処理し、在庫と予約を持ち越す |
| 需要予報 | 将来の来客は「少・中・多」の見込み。売上の確定予報にしない |
| 取消と変更 | 確定前は案を取り消せる。確定済み契約の変更は通常の交渉として扱い、無料取消にしない |
| 会話と経営の結末 | 最高利益を恋愛の条件にしない。意見に反対した夜や赤字の夜にも個別の交流を続ける |

具体例では、今夜の空室一室・食事の余力二食、明夜の空室二室から比較する。「一泊二食で120」なら今夜の部屋と二食を使い、明夜の二室は残る。「二泊・食事なしで120」なら同じ120を受け取るが明夜の空室は一室になり、今夜使わなかった材料が残る。どちらがよいかは、翌夜の需要や食材の状態で変わる。

### 実装前に仮ルールを決める点

| 未確定の点 | 最初の開発で行うこと |
| --- | --- |
| 承諾条件が分かるのに、希望を聞くため一枠使う理由 | 得られる情報が提案や人物理解をどう変えるかを説明する。何も変わらないボタンを置かず、試験する仮案か初回で保留する範囲を明記する |
| 維持費、食材価格、借入額、最終必要資金 | 試作用の値と単位をデータに置き、調整理由を記録する。企画で決定済みとは書かない |
| 食材の一食あたり使用量、食事の提供日、厨房休養、清掃・修繕 | 夜を進める順序と予約への影響を、再現可能なルールにする |
| 最大二案の提示と四枠の関係、予約の解禁時期、予約金の詳細 | どの操作で枠や現金が動くかを決め、原文に曖昧さがあれば仮仕様として記録する |
| エンジン、保存方式、最終アセット | スマホ縦画面と日本語、端末内保存に適する構成を選ぶ。選定理由を残す |

## 5. 二人の魅力とアート

マオは26歳の支配人。黒ボブ、黒いワンピースと白いエプロンが基本。先の予約を守るために余裕を残したい。仕事では几帳面だが、休日の喫茶店では菓子を選びきれず、主人公と分け合うことを楽しむ。

コハルは23歳の料理人。栗髪のゆるいサイドポニー、クリーム色の刺繍入り作業着が基本。今夜の客へ料理を届け、余りそうな材料も生かしたい。普段は気軽に話すが、自分の料理を主人公に褒められると照れる。

二人とも成人で、恋愛描写は全年齢。仕事と私生活の違い、表情差分、本人らしい照れ、過去の会話を受けた返事で魅力を作る。二人の意見にはそれぞれ理由を持たせ、相手に反対した後にも関係を描く。片方を経営上の正解役に固定せず、賛成による恒久的な能力強化を与えない。

本編の初期上限は、各ヒロイン二衣装・六表情・個別四話、イベントCG四点、背景は帳場・厨房・食堂・私室を中心とする。これらは制作予定で、生成済みアセット数ではない。初期案は静止した表情差分を使い、音声、Live2D、口パク、瞬きは制作量に含めていない。

素材は画風をそろえたオリジナル2Dを中心にする方針。企画の3面イメージを、切り出しだけで完成立ち絵と扱わない。Kenney Furniture KitとUI Audioは候補で、採用時に配布物とライセンスを再確認する。Tripoを使う場合は、ユーザーが挙げたWebブラウザ経由で扱う。2D作品を作るために3D生成を必須にする必要はない。調査に保存した他ゲームの画像79枚を本作の素材へ流用しない。

## 6. 次のセッションで推奨する最初の開発範囲

最初の作業単位は、三夜を通して実際に遊べる試作とする。この範囲は本引き継ぎでの推奨で、ユーザーが本編の規模を三夜へ変更したものではない。企画全体を書き直す前に、契約の判断と二人への関心が一緒に成立するかを確かめる。

1. 関連資料を読み、狙い、残す仕様、仮ルール、実装範囲を短い計画にまとめる。資料だけで決められる可逆な選択は、理由を残して進める。
2. 三夜の需要・客・厨房状態を作り、契約と営業終了時の処理をデータで再現する。入金、予約、食材、四枠の処理をそろえ、表示だけ結果が変わる状態を作らない。
3. タイトル、営業、台帳、夜の結果、二人との交流、基本設定、保存と再開を操作できるようにする。契約の比較・確定・取消と、原因になった過去の契約への往復を実装する。
4. 同じ金額でも条件が違う契約を比べる場面と、二人が違う意見を出す場面を用意する。利益が低い夜や反対した夜にも、本人らしい返答が続くことを確かめる。
5. 実画面で三夜を通して操作し、結果と次の予約が一致するかを確認する。試作で分かった問題と、まだ仮説のままの点を報告する。その結果から十八夜へ広げる順序を決める。

主な画面寸法は390×844、最低限の確認対象は360×800。主操作は高さ48px以上を目標とし、ドラッグや長押しを必須にしない。見出しは明朝系、本文と数値はゴシック系、生成りの紙・焦茶の文字・朱色の契約印という方向を引き継ぐ。文字、数字、枠、ボタン、フォーカス、成立印の反応も最初の画面から設計する。実文言と大きな値を使い、演出が契約条件や次の操作を隠さないことを確認する。

端末内の保存と再開、保存できない場合の再試行・書き出し、演出の動きを減らす設定、フォーカスが外れたときの停止も扱う。存在するボタンは実際の操作へ結び付け、未対応項目の表示方法を明確にする。

## 7. 検証と評価で間違えないこと

14作品の調査はLuna High、集約とスキル執筆は6.1 Sol、最終レビューはAstraが担当した。順位と画像ハッシュ、スキル構造、日本語、架空の設計課題への適用を確認した。既存ゲームを実機操作して面白さを実証したものではなく、スキルありの回答が通常回答より優れていると示した実験でもない。

企画書の末尾には「全員が満室だけを選ぶ場合は修正する」という古い評価条件が残る。調査後はこの考え方を改めた。同じ契約や満室を選んでも、目的と状態に合った理由があれば、それだけで失敗にしない。好感度、利益、正答率、継続時間、選択比率の均等化だけで面白さを評価しない。

| 確かめること | 観察・照合する内容 |
| --- | --- |
| 契約の処理 | A/Bの確定後の入金、空室、食事と材料、翌夜の予約が予告と一致する。二重予約や不足する契約を防ぐ |
| 夜をまたぐ理解 | 契約前の予測、選んだ理由、結果後の説明、次の判断の修正を記録する |
| 原因の追跡 | 後日の不足を過去の契約へ戻って説明できる。台帳を全部読む作業になっていないかを見る |
| 人物への関心 | 二人の人柄、選択時の意図、返答の受け止め、利益が低い夜にも関わりたいかを聞く |
| スマホ操作 | 二つの画面寸法で文字の欠け・重なり・はみ出し、確定前の取消、台帳往復、保存失敗、再開を実際に確認する |

予測を理解しても契約が作業に感じられる、会話の違いを読めても人物へ関心が持てない、といった結果も記録する。人間の試遊は実施後だけ実施済みとし、依頼できない場合は、エージェントの操作確認と区別して未実施と書く。企画にある五人程度の試遊も、これから行う検証案である。

実装先の設定にある適切なテスト・lint・型チェック・buildを選ぶ。特に、契約確定、夜の更新、保存と再開、表示予告と実結果の一致を検証する。今回の企画資料用Pythonや画面モックの検査を、新しいゲームの動作テストとして代用しない。日本語は`yomiyasu`のrun/verify、完了前はAstraの`ai_slop_reviewer`で確認する。
