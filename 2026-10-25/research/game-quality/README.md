# ゲームの良さを調べ、設計に使う

Steamの上位作品14作を調べ、ゲームの問題を診断し、設計を変えて試すためのスキルを作った。作品ごとのルールと画面から、何が判断や交流を支えているかを比較した。既存作品の楽しさを実証した研究ではない。

最初に読むものは、[スキル本体](../../../.agents/skills/game-quality-design/SKILL.md)と[14作品の比較](synthesis.md)。選定理由を確かめる場合は[対象一覧](selection.md)、調査方法は[計画](PLAN.md)、結果と限界は[検証記録](verification/RESULTS.md)を参照する。

## 使い方

`game-quality-design`を指定し、企画書や遊べる版、対象プレイヤー、目指す体験、困っている場面を渡す。たとえば次のように依頼できる。

> $game-quality-design を使って、この企画を評価してください。対象は短い時間に経営判断と人物交流を楽しみたい人です。毎日同じ契約ばかり選ぶ設計になっていないかを調べ、優先する変更と小さな試験を提案してください。

スキルは、問題のある場面、根拠、変える箇所、狙う効果、確かめ方をつなぐ。ゲームごとに目指す体験が違うため、罰、分岐、数値の損得を一律に要求しない。既存の`game-design`はループや個別の仕組みを詳しく考える際に併用できる。

## 調査を進めた順序

Stardew Valley、Slay the Spire、ELDEN RINGの3作から始めた。最初の評価では、前2作の主要なルールが不足していたため拡大を保留した。資料を補い、6.1 Solが再評価した後に9作を追加し、最後に物語と推理を扱う2作を補った。[試行評価](pilot-evaluation.md)に不足と修正理由を残している。

作品別の調査はLuna High、比較とスキルの執筆は6.1 Solが担当した。別の6.1 Solによる[使用試験](verification/FORWARD_TEST.md)では、スキルなしの回答も比較材料にした。Astraの最終レビューでは指摘がなかった。範囲と未確認事項は[検証記録](verification/RESULTS.md)に記載した。

## 資料と画像を確かめる

[対象一覧](selection.md)から各調査票へ進むと、出典、ルール、画像の観察、設計仮説、試作で確かめる案を読める。画像は`frames/`に置き、同じ番号のJSONに取得元と時刻、SHA-256を記録した。79枚には宣伝カットやHUDのない画像も含まれ、79件の操作を観察したという意味ではない。

`rankings.json`と`rankings-additional.json`は選定時点の順位、`catalog.json`はSteam公式APIから得た作品情報の要約である。公開ページは更新されるため、現在の表示が記録と違う場合がある。APIの応答本文、動画の一部、試行初稿、推敲記録はローカルの`raw/`と`verification/work/`に保存し、Gitには含めていない。

画像は調査の根拠として保存した。制作するゲームのキャラクター、背景、UI素材への流用を目的としない。

## 記録を検証する

```sh
python3 2026-10-25/research/game-quality/scripts/verify.py
```

このコマンドは、選定した作品と順位の対応、調査票の根拠ID、画像のハッシュを照合し、`verification/source-audit.json`を更新する。ルールの正しさ、文章の読みやすさ、ゲームの面白さは判定しない。

`scripts/collect.py`は公開されたSteamの情報と動画の指定フレームを取得する補助スクリプトで、Python標準ライブラリと外部の`ffmpeg`・`ffprobe`を使う。再取得は現在の情報になる。選定時点の記録を残すため、再調査では別の作業コピーで実行する。
