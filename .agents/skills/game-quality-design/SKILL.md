# ゲームを評価し、設計を変えて確かめる

既存の企画、対象プレイヤー、目指す体験、変えられる範囲から始める。「良い」はその人がその体験を得られるかで判断する。緊張、穏やかな反復、人物への愛着、推理の納得などを、常に同じ基準で採点しない。狙いが不明なら、評価を左右する前提だけ確認する。

このスキルだけでも使える。`game-design`が利用可能なら、ループや個別の仕組みを詳しく考える際に併用する。ここでは問題の診断、具体的な変更、効果の確認をつなぐ。実装を求められたら、採用した変更を対象エンジンのスキルへ渡す。

## 評価から変更へ

1. 何が良く、何が弱いかを先に述べる。 対象プレイヤーと狙う体験に照らし、現在の設計が支える部分と妨げる部分を挙げる。入力が企画書だけなら設計の評価、実際の試遊があれば体験の評価として範囲を示す。根拠不足を理由に評価全体を止めず、分かることと未確認を分ける。
2. 弱さが起きる場面を追う。 「単調」「分かりにくい」を、プレイヤーが何を知り、何をして、どう反応が返り、その後何が変わるかへ直す。[診断と試験](references/diagnosis.md)で、ルール・操作と表現・学習・失敗と進行・人物との関係のうち、原因に関わる部分だけ調べる。資源の代償、二択、分岐がない場面にも使う。
3. 狙いに合う最小の変更を選ぶ。 ルールが生む行動が弱いなら、表示や演出を足すだけで済ませない。行動が機能しているなら、情報、入力、反応、待ち時間の不足を探す。[条件付きの設計例](references/design-moves.md)は症状に合う項目だけ読む。機能数、罰、複雑さ、分岐を増やすことを解決にしない。
4. 何が変われば改善かを決める。 「この状態でこの変更をすると、この理由でプレイヤーの行動や体験がこう変わる。こうなら仮説を見直す」と書く。対象の目標や状態を変え、選択前の理解、行動、結果の受け止め、次の試行を観察する。試作や人間の試遊をまだ行っていなければ、検証案として返す。
5. 優先する変更と確かめ方を一緒に返す。 評価、重要な問題、根拠、変える箇所、狙う効果、失敗候補、次に行う最小の試験を結ぶ。良い部分も残し、実装範囲を勝手に広げない。

## 判断を誤らないために

- 記載されたルール、画面で見える事実、実際のプレイ行動、設計上の仮説を分ける。資料不足で主要な処理が分からないなら、その規則や画面を先に補う。
- 攻略を読む作者が知る結果と、選ぶ前のプレイヤーが知る情報を分ける。人物の本心や物語の先をすべて予告する必要はない。何を意図して選び、後でどう解釈できるかを確かめる。
- 同じ行動や同じ正答に収束しても、体験は成立しうる。選択の分散、正答率、継続時間、勝率だけを面白さの指標にしない。操作の気持ちよさ、理解、意図、感情、納得を狙いに合わせて調べる。
- 人物との交流を能力や好感度の回収だけに還元しない。相手固有の言動、過去の関わり、こちらへの応答を覚え、関わりたいと思えるかも見る。
- 静止画は配置や文言の例になるが、操作感や演出のタイミングの証拠にはならない。編集された別カットを行動と結果として結ばない。人気・売上から特定の仕組みの良さを断定しない。

## 調査例の読み方

[出典付きケース要旨](references/case-evidence.md)は2026-10-25に調べた14作品のルール資料と静止画の要旨。作品別の根拠ID、出典、バージョンと未確認範囲へ戻れる。人間の試遊や楽しさの実証は含まない。公式説明・開発者の意図・コミュニティ資料を区別し、数値をそのまま新作へ移さない。新しい事実として使う場合は対象バージョンと出典を確認する。
