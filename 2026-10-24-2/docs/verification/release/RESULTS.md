# 公開前の確認記録

ユーザーから、作業を終えたらmainにコミットしてGitHub Pagesで公開する追加依頼を受けた。基点は `35f58ebecaae971d8a8b3e62bb378dda78ca1ba8`。本書はその後の公開前確認を記録する。公開成功や公開配布物の照合を終えたことは示さない。再設計までの確認は[前段の記録](../rework/RESULTS.md)に残す。

## Chromeでのゴール到達

macOSのChromeをCUAのキーボード操作で動かし、900m地点のFINISHへ到達した。ポーズで小区間に分け、6回の落下復帰を使った。無停止の自然なプレイや、人間による難易度・面白さの評価とは区別する。

[結果画面](local-result.jpg)には次の値と保存メッセージが表示された。

| 項目 | 表示 |
| --- | --- |
| TIME | 01:03.13 |
| SCORE | 2,825 |
| FALLS | 6 |
| 保存 | 記録を保存しました |

TIMEは結果画面の値であり、ポーズを含む現実の所要時間ではない。[最後の跳躍](local-final-flight.jpg)、[最初の着地](local-first-landing.jpg)、[2か所目の着地](local-second-landing.jpg)、[落下後の復帰](local-recovery.jpg)、[再挑戦後のポーズ](local-retry-pause.jpg)を含む15枚を、この到達確認の画像として保存した。[再挑戦後のポーズ画面](local-retry-pause.jpg)ではTIME 00:00.48、SCORE 0、風力60を確認し、走行状態が初期化された。この到達確認だけで操作の習得しやすさや連続した動作の自然さを確認済みとはしない。

## 音とエフェクト

Godot 4.7.2のmacOS実行ファイルを `--headless --audio-driver Dummy` で動かした。実Mainからのloop、cue、音量設定、ポーズ、再開、リセットの接続を確認した。[検査条件と数値](sound-effects-summary.json)を保存している。

| 検査 | 条件と結果 |
| --- | --- |
| 接続と資源 | 61項目を確認。音声8ノード、描画4ノードとWAV・mesh・materialの資源IDを維持した |
| 繰り返し | 24,000更新、cue 1,000回、追加の着地演出422回。60Hz換算400秒相当の加速した部品更新であり、本編を400秒間遊んだ耐久試験ではない |
| 10回の観測 | Node 321、Object 2,234、Resource 57、Orphan 0が固定だった |
| 実Main全体を含む静的メモリ | 312,672,885から312,702,881バイトへ29,996バイト増加。検査用のチェック結果と観測記録の蓄積を含み、無期限にメモリが増えないことの証明ではない |
| 動きを減らす設定 | Mainから設定が渡ることは確認。Dummy描画ではMultiMeshの変換を正しく読み戻せず、速度線の非表示を数値で確認する1項目は未確認とした |

録音は実際のGodot Masterバスのfloatミックスから取得した。Masterは0dB、`soundscape` の音量は1.0で測り、通常設定のMaster 0.65より強い条件にした。聴感、Chromeでの音声出力、機器から出る音は評価していない。

| 録音条件 | ピーク | クリッピング相当のフルスケール到達サンプル |
| --- | ---: | ---: |
| 40m/s・旋回・ため・全cueの順次再生 | 0.275874 / −11.19dBFS | 0 |
| cleanとreleaseを交互に、4音声を同じフレームで32回そろえる負荷 | 0.897509 / −0.94dBFS | 0 |

後者のDC平均は−0.001131だった。ポーズ中の録音ピークは0、`set_volume(0)` の録音ピークは約−109.30dBFS。Mainのポーズでは音とエフェクトの時計が止まり、再開の合図を終えると再開し、リセットではcueと継続状態が初期化された。観測した録音にクリッピングはなかったが、任意の組み合わせやブラウザ出力まで確認した結果ではない。実行ログとWAVは検査用の `.cache/release-check/` に保存した。

## 配布準備と公開の境界

作品一覧のサムネイルがWeb出力に含まれない不備を修正した。`scripts/godot.mjs` で `docs/verification/rework/web-carve-release.jpg` を `dist/thumbnail.jpg` へコピーし、作品一覧の参照を `thumbnail.jpg` にした。ローカルの元画像と出力は81,915バイトで、SHA256の一致を[記録](originals/thumbnail-check.json)した。これは公開サーバーやCIの配布物を確認した結果ではない。

比較には成功した基準ビルドのrun `40093933322`、コミット `d8253e95b81938454e089e6378c4b1fd67e6f5e6`、artifact `12559574869` を使った。アーカイブ取得後にZIPのCRCを検査し、SHA256 `95fa8b08eb8b7f68419c509dc0db563a1a9507f1723cddb6ffdbb21584e0e596` がGitHubのdigestと一致した。今回変更するアプリは `2026-10-24-2` の1件で、再利用する25アプリの315ファイルをSHA256で照合し、不一致は0件だった。[組み立ての記録](site-assembly.json)に残す。

ルートの `npm test` は38検査、単体アプリの[検査とビルド](app-check.log)は6本のGodot検査とWeb出力が成功した。組み立て済みの出力をローカルの4252番ポートで開き、[作品一覧](local-showcase.jpg)から[ゲームのサブフォルダ](local-assembled-run.jpg)へクリックで移動した。サムネイルはDOMで読み込み完了と自然サイズ1282×779を確認した。サブフォルダでS+Dの旋回・解放・ポーズを操作し、観察したconsoleの警告・エラーは0件だった。これらはローカルでの配布構成の確認である。

公開自体は本記録の確定時点では未実施。公開後のWorkflow、対象コミット、配布物との照合、公開URLでの動作は別に確認し、[PR #202](https://github.com/hayatok/100challenge/pull/202)と[Issue #203](https://github.com/hayatok/100challenge/issues/203)へ結果を残す。公開先を利用可能とする案内は、その確認を終えてから行う。
